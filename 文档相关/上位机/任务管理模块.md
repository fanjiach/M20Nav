## 4.2.1 模块设计目标
基于机场廊桥巡检业务场景，任务管理模块需实现**高可靠、高实时、低冲突**的巡检任务全生命周期管控，核心目标如下：
1. 兼容绝影X30/M20双机型巡检任务，屏蔽机型差异对任务执行的影响；
2. 支持任务的接收、解析、存储、调度、执行、暂停/取消/恢复、结果上报全流程自动化；
3. 实现多机路段互斥执行，避免廊桥巡检路径冲突；
4. 保障任务优先级调度的准确性，核心应急任务（如急停、返航）可立即中断低优先级任务；
5. 支持任务断点续跑，异常恢复后无需重新执行已完成路径点；
6. 任务状态持久化存储，上位机重启后可恢复未完成任务；
7. 与版本同步、机器狗控制、异常处理模块解耦，通过标准化接口交互。

## 4.2.2 核心数据结构
### 4.2.2.1 任务基础结构体（JSON）
```json
{
  "task_id": "T20260513001",          // 任务唯一标识（服务器生成，格式：T+年月日+序号）
  "dog_id": "X30_001",                // 绑定机器狗ID
  "task_type": "patrol",              // 任务类型：patrol(巡检)/version_update(版本更新)/manual_control(手动遥控)
  "execute_time": "2026-05-13 14:00:00", // 任务执行时间（定时/立即：immediate）
  "priority": 3,                      // 任务优先级（1-5，1最高）
  "route_json": {                     // 任务路径JSON（点位编号数组）
    "route_id": "R008",               // 路线ID
    "point_ids": ["P001","P002","P003"], // 点位编号数组（由服务器下发）
    "patrol_times": 3,                  // 巡查次数N（定时任务在一次触发窗口内巡查N次）
    "repeat_daily": true,               // 是否每天按execute_time触发
    "return_to": "HOME",                // 任务完成后返回点位（可选；缺省则返回任务开始前的点位）
    "default_stay_time": 5              // 点位默认停留时间（可选）
  },
  "zip_url": "http://xxx/task.zip",    // 任务压缩包下载URL（zip）
  "map_md5": "e807f1fcf82d132f9bb018ca6738a19f", // 任务压缩包/地图包MD5（整体校验）
  "create_time": "2026-05-13 13:59:00", // 任务创建时间
  "seq_id": "SEQ20260513135900001",   // 消息序列号（防重放）
  "status": "pending"                 // 任务状态：pending(待执行)/executing(执行中)/paused(暂停)/cancelled(取消)/completed(完成)/failed(失败)
}
```

### 4.2.2.4 任务压缩包结构（zip）
任务压缩包为zip格式，解压后包含：
- 地图文件夹（机器狗导航所需全部地图文件）
- 地图路径json文件（人工配置，可到达点位与线段集合，包含所有点位与路径段信息）

上位机处理规则：
1. 下载zip并解压，识别“地图文件夹”和“地图路径json文件”
2. 将地图文件夹复制到机器狗指定目录（如`/opt/robot/maps/{task_id}/map/`）
3. 使用软链接将“当前地图路径”指向最新地图目录（如`ln -sfn /opt/robot/maps/{task_id}/map /opt/robot/current_map`）
4. 将地图路径json文件写入固定位置（如`/opt/robot/current_map_path.json`）供任务执行查点使用

### 4.2.2.5 地图路径json文件规范（标准结构）
地图路径json用于描述“该地图可到达的点”和“点之间可通行的线段”，用于任务执行时按点位编号查点与校验线段连通性（线段数据主要供机器狗导航使用，上位机任务模块当前只做端点有效性校验）。

#### 顶层字段（必选/可选）
```json
{
  "map_id": "MAP_001",
  "map_version": "2026.05.18",
  "home_point_id": "HOME",
  "points": [
    {
      "point_id": "P001",
      "name": "登机口-1",
      "coordinate": [116.5823, 39.9087, 0.5],
      "stay_time": 5,
      "detect_type": "navigation",
      "section_id": "S001",
      "section_occupy": true
    }
  ],
  "segments": [
    {
      "segment_id": "L001",
      "from": "P001",
      "to": "P002",
      "direction": "both"
    }
  ]
}
```

#### points（必选）
- 类型：数组或对象（推荐数组）
- 每个点位必含字段：
  - `point_id`：点位编号（全局唯一）
  - `coordinate`：三维坐标数组 `[x,y,z]`（可根据实际系统采用经纬度/局部坐标）
- 可选字段（建议保留，便于任务侧默认行为）：
  - `stay_time`：到点停留秒数
  - `detect_type`：到点执行动作类型（例如 navigation/recognition/patrol）
  - `section_id` + `section_occupy`：路段互斥控制（若任务点位需要互斥则在点位上标明）

#### segments（建议必选）
- 类型：数组
- 每个线段必含字段：
  - `from` / `to`：端点 point_id
- 约束：
  - `from/to` 必须在 points 中存在，否则视为非法地图路径json

#### home_point_id（推荐）
- 用于任务完成后返回点位的默认锚点
- 当服务器下发 `route_json.return_to = "HOME"` 时，上位机会解析为 `home_point_id` 对应的点位编号

### 4.2.2.2 任务执行上下文结构体
用于记录任务执行过程中的动态状态，保障断点续跑：
```json
{
  "task_id": "T20260513001",
  "current_point_id": "P008",         // 当前执行路径点ID
  "completed_points": ["P001","P002","P003","P004","P005","P006","P007"], // 已完成路径点
  "failed_points": [],                // 执行失败路径点
  "execute_start_time": "2026-05-13 14:00:05", // 任务实际启动时间
  "execute_duration": 300,            // 已执行时长（秒）
  "complete_rate": 0.35,              // 任务完成率（已完成点数/总点数）
  "last_error_code": 0,               // 最后一次错误码（0为无错误）
  "last_error_msg": "",               // 最后一次错误信息
  "occupy_sections": ["S001","S002"]  // 当前占用的路段ID
}
```

### 4.2.2.3 路段占用状态结构体
用于多机路段互斥校验，通过WebSocket与服务器实时同步：
```json
{
  "section_id": "S001",
  "dog_id": "X30_001",
  "occupy_status": "occupied",        // 占用状态：occupied(已占用)/free(空闲)/waiting(等待)
  "occupy_start_time": "2026-05-13 14:02:00", // 占用开始时间
  "timeout": 30,                      // 等待超时时间（秒）
  "seq_id": "SEQ20260513140200001"
}
```

## 4.2.3 任务生命周期管理
任务从接收至结束的全生命周期状态流转如下：
```
pending(待执行) 
  ↓（到达执行时间/手动触发）
executing(执行中) 
  ├─→ paused(暂停) ──→ executing(恢复执行)
  ├─→ cancelled(取消)（终止）
  ├─→ failed(失败)（终止，可重试）
  └─→ completed(完成)（终止）
```
- **状态变更触发条件**：
  1. `pending`：任务接收并校验通过后自动进入；
  2. `executing`：到达执行时间、版本/时间/机器狗状态校验通过、路段占用校验通过后进入；
  3. `paused`：接收服务器`task_pause`指令、手动触发暂停、高优先级任务抢占时进入；
  4. `cancelled`：接收服务器`task_cancel`指令、任务执行前校验失败（如地图MD5不匹配）时进入；
  5. `failed`：路径点执行失败（重试3次仍失败）、Level 3异常触发、机器狗失联时进入；
  6. `completed`：所有路径点执行完成、完成率100%时进入。


## 4.2.4 任务接收与校验流程
### 4.2.4.1 任务接收（与WebSocket模块交互）
1. WebSocket模块接收服务器`task_push`消息，转发至任务管理模块；
2. 任务管理模块首先校验`seq_id`唯一性（本地缓存近1小时seq_id，避免重复任务）；
3. 校验通过后，解析消息体，填充`task_id`/`dog_id`/`priority`等核心字段，生成任务基础结构体；
4. 任务暂存至内存队列，同时异步写入本地SQLite数据库（持久化）；
5. 向WebSocket模块返回`task_ack`回执（ack_result=success/fail，失败需携带错误码）。

### 4.2.4.2 任务前置校验（执行前必做）
任务到达执行时间前10秒触发前置校验，未通过则标记任务`failed`并上报：
| 校验项                | 校验规则                                                                 | 错误码  | 处理策略                     |
|---------------------|----------------------------------------------------------------------|-------|--------------------------|
| 机型匹配校验            | 任务绑定dog_id与当前机器狗ID一致，且任务类型适配机型（X30/M20）| 3000  | 拒绝执行，上报“机型不匹配”          |
| 版本校验              | 任务关联map_md5与版本同步模块当前地图MD5一致                              | 3002  | 触发版本同步模块下载地图，超时未完成则任务失败 |
| 时间同步校验            | 本地时间与服务器时间时差≤5秒（通过time_sync模块同步）| 3003  | 触发时间同步，同步失败则任务失败       |
| 机器狗状态校验          | 机器狗在线、电量≥20%、无Level 2/3异常、姿态正常（起立/可运动）| 3004  | 等待机器狗状态恢复，超时30秒则任务失败   |
| 网络状态校验            | WebSocket连接正常、局域网（机器狗通信）通断正常                             | 3005  | 触发网络重连，重连失败则任务失败       |
| 路径点合法性校验          | 路径点坐标在预设巡检区域内、section_id有效、detect_type适配当前机型          | 3006  | 拒绝执行，上报“路径点参数非法”        |

## 4.2.5 任务调度机制
### 4.2.5.1 调度核心算法
采用**优先级+定时（到点触发）**策略，当前仓库实现基于`asyncio`轮询调度：
1. 周期性扫描本地SQLite中`pending`任务（默认0.5s一次）；
2. 过滤出已到达`execute_time`或`execute_time=immediate`的任务；
3. 按优先级（1最高）与执行时间排序后，取首个任务进入执行；
4. 单机单任务串行执行，执行中任务不并发（便于后续加入抢占/恢复机制）。

注：文档中的抢占式调度（优先级1/2抢占）在当前版本可作为下一步增强项实现。

### 4.2.5.2 优先级调度细则（补充原有规则）
| 优先级 | 任务类型       | 抢占规则                                                                 | 恢复规则                                   |
|-----|------------|----------------------------------------------------------------------|----------------------------------------|
| 1   | 紧急返航/急停   | 立即中断所有类型任务，关闭机器狗运动控制通道，禁止其他任务抢占                  | 急停/返航完成后，需人工确认是否恢复原任务          |
| 2   | 手动遥控       | 暂停当前自动巡检任务，遥控指令有效期内独占执行，禁止同优先级任务抢占              | 遥控超时（5s）/手动退出后，自动恢复原任务断点续跑     |
| 3   | 实时巡检任务     | 可抢占优先级4/5任务，不可抢占1/2任务，抢占时需先释放被抢占任务的路段占用          | 抢占完成后，恢复被抢占任务（断点续跑）             |
| 4   | 定时巡检任务     | 仅可被1/2/3优先级任务抢占，抢占后记录断点，禁止抢占其他任务                    | 抢占任务完成后，自动恢复（断点续跑）               |
| 5   | 版本更新/数据同步 | 仅在无其他任务时执行，任意高优先级任务可抢占，抢占后中断更新，恢复后重新校验版本再执行 | 抢占任务完成后，重新触发版本同步（断点续传下载）     |

## 4.2.6 路径点管理与互斥机制
### 4.2.6.1 路径点执行流程
1. 任务进入`executing`状态后，初始化路径点队列（按route_json中points顺序）；
2. 取出首个路径点，执行**路段占用校验**（仅对section_occupy=true的路段）；
3. 校验通过后，向机器狗控制模块下发导航指令（携带point_id、coordinate、stay_time）；
4. 等待机器狗控制模块返回执行结果（成功/失败）：
   - 成功：标记该路径点为已完成，更新完成率，上报执行进度；
   - 失败：重试3次，仍失败则标记为failed_points，触发Level 2异常，继续执行下一路径点；
5. 重复步骤2-4，直至所有路径点执行完成/任务被暂停/取消/失败。

### 4.2.6.2 路段互斥机制（细化）
#### 互斥校验流程
1. 提取当前路径点及后续4个路径点的section_id（提前预判，减少等待）；
2. 筛选出section_occupy=true的路段，生成路段占用校验请求（section_check消息），通过WebSocket发送至服务器；
3. 服务器返回路段占用状态：
   - 空闲（free）：标记路段为occupied（携带当前dog_id和时间戳），下发导航指令；
   - 已占用（occupied）：进入等待状态（1s轮询一次服务器），最大等待30秒；
   - 等待超时：触发Level 2异常（错误码3001），上报“路段占用超时”，跳过该路径点（标记为failed）；
4. 路径点执行完成/异常中断后，立即发送路段释放请求（section_check消息，occupy_status=free），释放超时未回执则重复发送3次。

#### 防死锁设计
1. 路段占用有效期：标记占用后，若10秒内未下发导航指令，自动释放路段；
2. 互斥范围限制：仅廊桥核心交汇路段（如S001/S002/S003）启用互斥，非核心路段（如独立巡检段）无需互斥；
3. 强制释放机制：服务器检测到某机器狗占用路段超过预设时长（如5分钟）且无任务执行时，强制释放路段并通知对应机器狗。

## 4.2.7 任务暂停/取消/恢复逻辑
### 4.2.7.1 任务暂停
1. 接收服务器`task_pause`指令（携带task_id、pause_reason、operator）；
2. 立即停止当前路径点执行（向机器狗控制模块下发暂停指令）；
3. 释放当前占用的所有路段（发送section_check释放请求）；
4. 更新任务状态为`paused`，记录暂停原因和操作人；
5. 向服务器上报暂停结果（task_ack），携带暂停时间和当前断点；
6. 暂停期间，任务上下文持久化至数据库，保障重启后可恢复。

### 4.2.7.2 任务取消
1. 接收服务器`task_cancel`指令（携带task_id、cancel_reason、operator）；
2. 立即停止所有路径点执行，下发机器狗急停指令（若运动中）；
3. 释放所有占用路段，清理任务执行上下文；
4. 更新任务状态为`cancelled`，记录取消原因和操作人；
5. 向服务器上报取消结果（task_ack），任务终止，不可恢复。

### 4.2.7.3 任务恢复
1. 接收服务器“任务恢复”指令（扩展msg_type：task_resume）；
2. 从数据库加载任务执行上下文，定位当前断点（current_point_id）；
3. 重新执行前置校验（版本/时间/机器狗状态）；
4. 校验通过后，重新校验当前路径点的路段占用状态；
5. 路段可用则下发导航指令，恢复任务执行（状态更新为executing）；
6. 向服务器上报恢复结果（task_ack），携带恢复后的断点信息。

## 4.2.8 任务结果上报与断点续跑
### 4.2.8.1 任务进度/结果上报
- **进度上报**：每完成1个路径点，立即通过WebSocket模块发送`result_upload`消息，核心字段：
  ```json
  {
    "msg_type": "result_upload",
    "task_id": "T20260513001",
    "execute_result": "executing",
    "complete_rate": 0.35,
    "execute_duration": 300,
    "error_detail": "",
    "current_point_id": "P008",
    "dog_id": "X30_001",
    "timestamp": "2026-05-13 14:05:00",
    "seq_id": "SEQ20260513140500001"
  }
  ```
- **结果上报**：任务完成/失败/取消后，发送最终`result_upload`消息，补充：
  - 完成：execute_result="completed"，error_detail=""，complete_rate=1.0；
  - 失败：execute_result="failed"，error_detail=错误原因，last_error_code=对应错误码；
  - 取消：execute_result="cancelled"，error_detail=取消原因。

### 4.2.8.2 断点续跑机制
1. 任务异常中断（如网络断开、机器狗低电量、Level 2异常）后，任务状态更新为`failed`，但保留执行上下文；
2. 异常恢复后（如网络重连、电量恢复、人工处理异常），服务器可下发“断点续跑”指令；
3. 任务管理模块加载历史执行上下文，跳过已完成路径点，从`current_point_id`开始执行；
4. 若原当前路径点执行失败，续跑时先重试该路径点（3次），仍失败则标记为failed_points，继续下一个；
5. 续跑完成后，上报最终结果（含断点续跑次数、失败路径点明细）。

### 4.2.9.2 持久化策略
1. 实时写入：任务状态变更、路径点执行完成/失败、路段占用/释放时，立即更新数据库；
2. 定期备份：每小时备份一次数据库文件至`./backup/task_db/`目录，保留最近7天备份；
3. 异常恢复：上位机重启后，任务管理模块首先加载数据库中`pending`/`executing`/`paused`状态的任务，恢复至内存队列；
4. 数据清理：每月清理一次`completed`/`cancelled`状态超过30天的任务数据（保留日志文件）。

## 4.2.11 异常场景与处理细则
| 异常场景                | 异常等级 | 错误码  | 处理流程                                                                 |
|-----------------------|-------|-------|----------------------------------------------------------------------|
| 任务seq_id重复           | 警告   | 3007  | 丢弃重复任务，返回task_ack（success），日志记录重复原因                     |
| 路段占用等待超时          | 错误   | 3001  | 标记当前路径点失败，触发视频切片，上报异常，继续执行下一路径点                  |
| 路径点导航指令执行失败（重试3次） | 错误   | 3008  | 标记该路径点为failed_points，更新完成率，上报进度，继续下一路径点               |
| 任务执行中机器狗失联        | 致命   | 3009  | 立即暂停任务，释放路段，上报Level 3异常，触发自动返航模块                     |
| 任务执行中WebSocket断开     | 致命   | 3010  | 暂停任务，触发WebSocket重连，重连成功后恢复任务（断点续跑），重连失败则任务失败       |
| 任务数据库写入失败         | 警告   | 3011  | 重试写入（3次），仍失败则内存缓存任务信息，每10秒重试一次，直至写入成功           |
| 路径点坐标越界（超出电子围栏） | 致命   | 3012  | 立即停止任务，下发急停指令，上报Level 3异常，触发自动返航模块                   |
| 高优先级任务抢占时路段释放失败 | 错误   | 3013  | 强制发送路段释放请求（3次），仍失败则上报服务器，由服务器强制释放路段             |

## 4.2.12 性能优化策略
1. **路径点预加载**：任务执行前，预加载后续10个路径点的坐标、路段信息至内存，减少实时解析耗时；
2. **异步并发处理**：路段占用校验、任务结果上报、数据库写入等非核心流程采用asyncio异步执行，不阻塞路径点执行；
3. **内存缓存优化**：仅缓存当前执行中任务和待执行高优先级任务（前10个）的完整信息，低优先级任务仅缓存基础字段，降低内存占用；
4. **数据库索引优化**：为task_info表的task_id、status、priority字段建立索引，task_context表的task_id字段建立索引，提升查询效率；
5. **批量上报**：非核心进度（如路径点执行中）采用批量上报（每3个路径点上报一次），减少WebSocket通信频次。
